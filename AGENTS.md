# creview

Extension for oh-my-pi (omp) and pi (`@earendil-works/pi-coding-agent`) that implements the `/creview` commands: cross code review, where several models review the same diff in parallel, grouped into **presets**. Both hosts offer the same commands, menus and report format over one `creview.json`, with shared reviewers and separate preset maps per host.

## Structure: one file for both hosts

- **`extensions/creview.ts`** is the whole extension. `package.json` names it under both keys, `"omp": { "extensions": ["./extensions/creview.ts"] }` and `"pi": { "extensions": ["./extensions/creview.ts"] }`; omp reads `pkg.omp ?? pkg.pi`, pi reads `pi`.
- **No runtime host imports:** the only imports from `@oh-my-pi/*` and `@earendil-works/*` are `import type` (erased when loaded). pi cannot resolve `@oh-my-pi/*` at all (a runtime import of it stops pi at startup), and omp serves `@oh-my-pi/*` only to static imports, so the file implements the few host helpers it needs itself: the git steps of the Review Mode menu, the key checks (`isKey`) and pi's thinking levels (`piLevels`).
- **Host detection:** the default export takes either host's `ExtensionAPI` (typed `Api`, the members both share) and picks a `Host` once: `"arktype" in api` (omp injects its schema builders there; pi doesn't) selects `ompHost`, otherwise `piHost`.
- **`Host` (what differs per host):** host identity selects its preset map; `agents` (omp generates `agents/`; pi does not), `select` (rows with descriptions and checklist options), `models` (Add model's list and levels), `review` (run the reviewers) and `unusable` (why the host can't run a reviewer's model) handle host behavior. The command flows remain shared.
- **One shared `reviewers` map, filtered per host:** `creview.json` keeps every reviewer of both hosts; a reviewer's model must exist in the host that runs the review, and Add model offers that host's models. `host.unusable(ctx, model)` decides what a host can run. pi uses its pre-flight (`resolveModel`: model known, credentials, level supported); omp uses `ctx.models.list()` (only models with credentials, so an unknown model and a missing login look alike): `provider/id` must be listed and a `:level` must be one of the levels Add model offers for it (omp would clamp it instead).
- **Where it applies:** the reviewer picker (Create, Add) hides reviewers the host can't run; List and Remove reviewers show every member and mark those with `(<host> can't run it: <reason>)`. Preset descriptions, `/creview <preset>` and the omp `agents/` sync ignore it (pi still skips such members with its warning).

## Installation: each host reads this folder directly

omp: `config.yml` (`~/.omp/agent/config.yml`) lists the folder:

```yaml
extensions:
  - /path/to/creview
```

pi: `pi install /path/to/creview` adds the path to `packages` in `~/.pi/agent/settings.json` (`-l`: the project's `.pi/settings.json`). A local path is loaded in place, not copied.

There is no other copy: nothing of this package lives under `~/.omp/agent/` or `~/.pi/agent/`.

- **Data root:** `creview.json`, `agents/` and `templates/` resolve from the package root, the parent of `extensions/` (`fileURLToPath(import.meta.url)`; omp's URL carries a `?mtime=` query, and pi's loader has no `import.meta.dir`). `/creview-config` writes here, in both hosts.
- **Agents (omp only):** omp discovers `agents/*.md` of this package as task agents (extension package roots, see `omp://task-agent-discovery.md`). A same-named agent in `~/.omp/agent/agents/` or in a project's `.omp/agents/` wins over the one here, so don't keep `reviewer*.md` copies there. pi never reads `agents/`.
- **Template is not an agent:** `templates/reviewer.md` is outside `agents/`, so it is not discovered. The name `reviewer` (used by `/review`) therefore resolves to omp's bundled reviewer, and `task.agentModelOverrides.reviewer` in `config.yml` still applies to it. Keep only generated `reviewer-<name>.md` files in `agents/`.
- **Not in git:** `.gitignore` excludes `agents/` (generated) and `creview.json` (the user's own reviewers and presets). A fresh clone has neither: the first omp `session_start` creates an empty `agents/` (`syncAgents` uses `mkdirSync(..., { recursive: true })`), a missing `creview.json` means "no presets", and the first add in `/creview-config` writes `creview.json` (and, in omp, `agents/`).
- **Line ends:** `.gitattributes` (`* text=auto eol=lf`) keeps LF in checkouts. `renderAgents` also reads the template with `\r\n` turned into `\n`, so a CRLF template still matches `MODEL_BLOCK`; agent files are always written with LF.
- **`assets/`:** `logo.png` and the README screenshots (`*.png`, captured by hand from the real omp TUI with a neutral fixture). Not code; nothing reads them.

## Commands

`/creview` only starts reviews; `/creview-config` manages presets through a menu. Both are registered by the default export of `extensions/creview.ts`. The bullets below describe omp; pi follows them except where the pi section says otherwise.

```
/creview                                      pick a preset, then a Review Mode, and run the review
/creview <preset>                             pick a Review Mode, then run the review (no UI: default scope)
/creview <preset> <scope and instructions>    run the review with that scope
/creview-config                               menu: list, create or remove a preset, add or remove reviewers (no UI: list)
```

- **Presets only:** `/creview <x>` runs preset `<x>`; anything else is an error listing the presets, and nothing is sent. Without arguments and without a UI, `/creview` is a usage error pointing to `/creview-config`. A review with a single model is omp's own `/review`, not this extension; the former single-model commands (`/<name>-review`) are gone.
- **No presets yet for this host** (`creview.json` missing, `{}`, or the current host's preset map empty): `/creview` in every form (bare or typed, with or without a UI) is the single error `No review presets yet. Run /creview-config and choose "Create a preset".` (`NO_PRESETS`), checked before anything else. `/creview-config` List shows the same text, and "Remove a preset", "Add reviewers to a preset" and "Remove reviewers from a preset" give it as an error instead of an empty picker (`presetOptions`). "Create a preset" works; with no reviewers yet its reviewer picker offers only "Add model". A missing `creview.json` reads as `{ "reviewers": {}, "presets": { "omp": {}, "pi": {} } }`, and the first write creates it.
- **Running a review:** sends a prompt to the main agent (`pi.sendUserMessage`) asking for a single `task` call with one item per member (`agent: "reviewer-<name>"`). The agent then consolidates the results: consensus findings first, each naming the reviewers that flagged it (a `Reviewers` column or a `[a, b]` tag), then findings grouped P0 to P3 tagged with the reviewer(s) that found each one (partial agreement stated, distinct findings not merged), and a final verdict of APPROVE, COMMENT or REQUEST_CHANGES.
- **Review pickers** (only when `ctx.hasUI`): without a preset, `ctx.ui.select` for the preset (label: the preset name, description: its members). Without a scope, the "Review Mode" menu of omp's `/review`, with the same labels: `1. Review against a base branch (PR Style)`, `2. Review uncommitted changes`, `3. Review a specific commit`, `4. Review a specific PR/MR`, `5. Custom review instructions`. `pickScope` returns `{ scope, diff? }`. Cancelling any dialog sends nothing and notifies "Cancelled; nothing changed.".
- **Review prompt (`reviewPrompt(members, scope, diff?)`):** without `diff` (a typed scope, the no-UI default, or mode 5) it is the generic prompt: "Determine the review scope from `<scope>` (default to …)" and step 1 "Run `git status` and `git diff --stat` …"; typed prompts must stay byte-identical. With `diff` (modes 1 to 4), the opening is "Review scope: `<scope>`." and step 1 states the exact commands, then "Do this once so all reviewers inspect the exact same change set, and pass the target and these commands to every reviewer.". Steps 2 and 3 (one `task` call with every member, consensus, P0 to P3, verdict) are the same text in both.
- **Review Mode modes 1 to 3 (`resolveLocal`):** the git steps and sub-pickers of omp's `/review`, with its labels and messages, run through `api.exec("git", …)` in `ctx.cwd` (the same code in both hosts; omp's own module is internal and can't be imported). Base branch: "Select base branch to compare against" over local and remote branches (`for-each-ref`, `*/HEAD` dropped), then `merge-base` and `diff --quiet` against the current branch. Uncommitted: `rev-parse --git-dir` (outside a repository `git diff` would fall back to `--no-index`), then `diff --quiet` and `diff --cached --quiet`. Commit: "Select commit to review" over `log -n 20 --format=%h %s`, then `show --stat`. A failure ("No git branches found", "No commits found", "No uncommitted changes found", "No changes between <base> and <head>", "No common history between …", "Commit has no diff content", "Failed to get diff: <first stderr line>", "Failed to get commit: …") is one error notification and nothing is sent. Unlike omp's `/review`, there is no jj support and no filtering of unreviewable files. Mode 4 asks for a PR/MR number or URL with `ctx.ui.input` (omp's open-PR picker is not exported), and mode 5 asks for the instructions the same way; empty input cancels.
- **Scope strings:** mode 1 `the current branch against <base>, PR style (git diff <base>...HEAD)`; mode 2 `uncommitted changes (staged and unstaged)`; mode 3 `commit <short hash>`; mode 4 `PR/MR #<n>` for a number (`#`/`!` prefix accepted) or `PR/MR <text>` for a URL; mode 5 the instructions as typed (trimmed). No backticks: the prompt already wraps the scope in them.
- **Diff instructions:**
  - mode 1: `git diff <base>...HEAD` (overview `git diff --stat <base>...HEAD`);
  - mode 2: `git status`, `git diff` (unstaged) and `git diff --cached` (staged) (overview `git diff --stat` and `git diff --cached --stat`);
  - mode 3: `git show <hash>` (overview `git show --stat <hash>`);
  - mode 4: a number tries `gh pr diff <n>` (context `gh pr view <n>`) and falls back to `glab mr diff <n>` (context `glab mr view <n>`); a URL whose host contains `github` uses `gh pr diff <url>`, one containing `gitlab` uses `glab mr diff <url>`, any other input tells the agent to fetch the diff from it. Every PR/MR instruction adds that the PR/MR is not the local working tree, so no `git status` or `git diff --stat`;
  - mode 5: none (generic step 1).
- **`/creview-config`:** menu only. With a UI, `ctx.ui.select` "creview config" over the `CONFIG` entries (label → flow returning the notification text): "List presets and reviewers", "Create a preset", "Remove a preset", "Add reviewers to a preset", "Remove reviewers from a preset". Without a UI it notifies the list (read-only). Any argument is a usage error: there are no typed forms. Cancelling any dialog writes nothing and notifies "Cancelled; nothing changed.".
- **A preset is never empty:** "Create a preset" always adds at least one reviewer, removing all members is refused, and only "Remove a preset" deletes a preset. Emptied presets are no longer dropped automatically.
- **Checklist (`pickMany`, shared by Create, Add and Remove reviewers and by the model checklist):** a loop on `ctx.ui.select`, like omp's own `ask` tool. Checkbox rows first: one per candidate, label the plain reviewer name (or `provider/id` in the model checklist), description the model. Then "Add model" (`ADD_MODEL`, reviewer picker only, via `addRows`). Every call passes `{ initialIndex, selectionMarker: "checkbox", checkedIndices, markableCount }`: `checkedIndices` are the ticked rows, `markableCount` is the number of checkbox rows (pending new models included), so "Add model" keeps the plain cursor. Two modes, one loop, switched on `ctx.mode === "tui"`:
  - TUI: Space on a checkbox row toggles it and reopens the list with the cursor on that row; Enter on a checkbox row confirms the ticked rows as they are (the row under the cursor is not toggled). There is no Done row; the call also passes `helpText`, which replaces the selector's footer: `Space toggles · Enter confirms · Esc cancels`, plus ` · Enter on Add model opens the model list` in the reviewer picker.
  - Other hosts (RPC, ACP, which have no terminal input): Enter on a checkbox row toggles it, and a `Done (<n> selected)` row confirms; no `helpText`.
  - Either way Enter (or Space) on "Add model" runs it at once, the ticks are kept, and Esc on the list is cancelled. Confirming returns the ticked names in list order. There is no ask dialog and no timeout. Labels are capitalized ("Add model", "Done", "Thinking level for …", "Reviewer name for …"); "(none)" and the menu title "creview config" (the command name) stay lowercase.
- **Space key:** the TUI select binds only Enter, so in TUI mode `pickMany` registers `ctx.ui.onTerminalInput(onKey)` just before each select and removes it in `finally`. `onKey` records whether the key was an unmodified Space (`isKey(data, " ")`: the byte `" "`, or its kitty form `\x1b[32u` / `\x1b[32;1u` with event type press `:1` or repeat `:2`, Caps/Num Lock bits ignored; release `:3` and any Shift/Alt/Ctrl/Super modifier are not Space; the same answers as omp's `matchesKey(data, "space")`, except that a release never counts) and rewrites it to `{ data: "\r" }`, so the focused selector sees Enter; every other key passes through and clears the flag. Both hosts hand release events to input listeners when the kitty protocol is on, hence the explicit release check. The flag is reset before each select, so the last key decides: a space toggles, a real Enter confirms. It is never registered for the menu, the preset, level or confirm selects or the name input, so Space types normally there and in the editor afterwards. The mode check is `ctx.mode`, not the presence of `onTerminalInput`: every UI context has that method, but only the TUI's is real; RPC and ACP define it as a no-op. Trade-off: while a checklist is open a space cannot be typed into its search query (it toggles the row instead).
- **Search in a checklist:** omp 18.22's selector turns on type-to-search when the rows exceed `maxVisible` (max(4, min(15, terminal rows − 12))), so the model checklist (hundreds of models) is searchable and short reviewer lists usually are not. Each toggle reopens a new select, so the query is lost after every tick; the cursor stays on the ticked row of the full list.
- **Host support:** the checkbox look and the cursor staying on the toggled row depend on the host honoring those dialog options. The TUI controller forwards `initialIndex`, `selectionMarker`, `checkedIndices`, `markableCount` and `helpText` to its selector. RPC in the installed omp 18.22 puts the same four checklist fields in the `extension_ui_request` select payload (next to `title`, `options`, `optionDetails`, `timeout`), so the RPC client decides whether to draw them; older omp sources (18.14, `requestRpcSelect`) send only title, labels, descriptions and timeout. ACP sends only the labels as a string enum (no descriptions). Where the options are dropped, the toggle still works, but no row shows its checked state (only the `Done (<n> selected)` count) and the cursor goes back to the first row. Accepted because the TUI is the target and the loop stays usable elsewhere; there is no fallback code.
- **Reviewer picker (`pickReviewers`, shared by Create and Add):** the checklist "Add which reviewers to <p>?" over the `reviewers` not yet in the preset that this host can run (none left: only "Add model"). Enter or Space on "Add model" opens the batch flow at once (`newReviewers`): the checklist "Add which models?" over `ctx.models.list()` (`provider/id`, no "Add model" row), minus the models already pending from earlier batches (so a model cannot be added twice); then, for each ticked model in list order, a thinking level select "Thinking level for <provider/id>" ("(none)" plus the model's `thinking.efforts`, a fixed list for reasoning models without them, no step for non-reasoning models) and the name with `ctx.ui.input` "Reviewer name for <provider/id> (empty for <default>)" (placeholder and empty input: the default name below). Esc on the model checklist, confirming it with nothing ticked, or cancelling any level or name step drops the whole batch and returns to the reviewer list unchanged (ticks kept, cursor on "Add model"). Otherwise every new reviewer joins the list as a ticked row (description: its model) and the list reopens on the first of them; they are pending, nothing is written yet. "Add model" can be used several times; a name already in the list just ticks that row (a different model is caught at the end). It returns the ticked reviewers as `{ name, model? }[]` (`[]` when nothing is ticked).
- **Default reviewer name (`defaultName`):** the model id with provider and `:level` dropped, lowercased, every run outside `[a-z0-9]` turned into `-`, hyphens trimmed (`opencode-go/glm-5.3` gives `glm-5-3`). When a saved reviewer (either host's, even one hidden here) or a pending one has that name with another model, the default becomes `<derived>-<provider slug>`, then `-2`, `-3`... until free; with the same model it stays and the reviewer just joins. Only the default moves aside: a typed colliding name is still the `add()` error below.
- **One write (`add(preset, entries, isNew)`):** validates the preset and every entry first: at least one entry (`A preset needs at least one reviewer`), names `[a-z0-9-]+`, existing reviewers known; a new-model entry whose name is not in `reviewers` is added with the model, one there with the same model just joins, one there with another model (in `reviewers` or made earlier in the same checklist, in the same batch or another) is an error naming the existing model: `"<n>" is taken by a reviewer this host can't run (<model>); pick another name` when `host.unusable` says so (the picker hides that reviewer), otherwise `"<n>" is already used by <model>; pick another name`. Product messages never suggest editing `creview.json`. Any error writes nothing, not even the other ticked reviewers; the user can run the entry again. Then one `writeData` and one `syncAgents`; existing reviewers only join (no agent file changes). Add never changes an existing reviewer's model. The message lists what joined, `<p>: +a, +b (now: <members>)`, prefixed by `Wrote agents/reviewer-<a>.md (<model>), agents/reviewer-<b>.md (<model>); ` when reviewers were created.
- **Create a preset:** `ctx.ui.input` for the name, checked at once (`checkPreset(..., true)`: `[a-z0-9-]+` and not an existing preset, otherwise an error), then the reviewer picker; `add(..., isNew = true)` repeats the checks before writing and reports `Created preset <p>: <members>`. Nothing ticked is the error `A preset needs at least one reviewer`.
- **Remove a preset:** select the preset (description: its members), then `ctx.ui.confirm` ("Remove preset <p>?", "Its reviewers stay available."). Yes deletes the preset only; `reviewers` and `agents/` are untouched. No or cancel changes nothing.
- **Add reviewers to a preset:** existing presets only (no "new preset…" entry), then the reviewer picker. Nothing ticked notifies "Nothing selected; nothing changed.".
- **Remove reviewers from a preset (`rm(preset, names)`):** select the preset, then the checklist "Remove which reviewers from <p>?" over its members (description: the model), without "Add model". A preset with a single member skips the checklist: error `<p> has one reviewer; use Remove a preset`. Nothing ticked notifies "Nothing selected; nothing changed."; ticking every member is the error `<p> would be empty; use Remove a preset`; a name that is not a member is an error. Checks run before the one `writeData`; nothing else is written. The reviewers leave that preset only; they stay in `reviewers` (and their agent files stay), so they can be added back. The message lists what left: `<p>: -a, -b (now: <members>)`.
- **Changing a reviewer's model (developer note, not offered to users):** no menu does it; edit its entry in `creview.json`; in omp `agents/` regenerates at the next session start, in pi the next review uses it.

## pi

pi has no task tool and no agent files, so `piHost` runs the reviewers itself. Everything else (commands, menus, messages, `creview.json` writes) is the shared code above.

- **No `agents/`:** `host.agents` is false, so the `session_start` sync is not registered and `add` writes only `creview.json`; its message starts `Added reviewer-<name> (<model>)` instead of `Wrote agents/reviewer-<name>.md (<model>)`. The name and model checks are the same.
- **Select (`piSelect`):** pi's `ctx.ui.select` takes plain strings only (no descriptions, initial row or checkbox marks). Plain string menus (the config menu, Review Mode, branch and commit lists) use it. Everything else gets, in the TUI, a `ctx.ui.custom` list in pi's selector frame (`→` cursor, `[x]`/`[ ]` marks, description after the label, `initialIndex`, `helpText` footer, type-to-search when there are more than 10 rows, Backspace through pi's `tui.editor.deleteCharBackward` binding, `(n/total)` under a long list); every line is cut to the terminal width by `fit` (pi stops on a wider line), which counts one column per character. In RPC the rows become `"[x] label - description"` strings and the pick is mapped back to its label. The Space trick of `pickMany` works unchanged: pi's `ctx.ui.onTerminalInput` has the same `{ data, consume }` result in the TUI and is a no-op in RPC.
- **Add model:** `ctx.modelRegistry.getAvailable()` (models with credentials), levels from `piLevels(model)` without `off`. With no such model it is the error `pi has no model with credentials. Run /login or set a provider API key, then try again.`
- **Thinking levels (`piLevels`, pi-ai's `getSupportedThinkingLevels` rewritten here):** pi's levels are `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`; `xhigh` and `max` exist only for models whose `thinkingLevelMap` maps them, a level mapped to `null` is unsupported, and non-reasoning models have only `off`. A reviewer `provider/id:level` runs as `--model provider/id --thinking level`.
- **Pre-flight (`resolveModel`):** before anything is spawned, every member of the preset is resolved against pi's registry: `find(provider, id)`, else the part after the last `:` is the level and the rest the id; then the level must be one of the model's levels (no clamping), and `hasConfiguredAuth(model)` must hold. Reasons: `unknown reviewer`, `unknown model "<provider/id>"`, `unsupported thinking level "<level>"`, `no credentials for provider "<provider>"`. List shows the same reason after the model: `  reviewer-x  <model>  (pi can't run it: <reason>)`.
- **Skipped reviewers:** if none resolves, nothing is spawned or sent: error `No reviewer of this preset can run in pi: reviewer-a (<reason>), …`. Otherwise one warning `Skipping reviewers pi can't run: reviewer-a (<reason>), …. Running reviewer-b, ….` and the rest run.
- **Start notice:** right after that warning, one info notify `Running <n> reviewers in parallel: reviewer-a, ….` (`Running 1 reviewer: …`; ` Esc cancels.` appended in the TUI), because the chat stays empty until the synthesis; it stays in the chat and is not part of the LLM context.
- **Reviewer process (`runReviewer`):** `pi --mode json -p --no-session --model <provider/id> [--thinking <level>] --no-extensions --no-skills --no-prompt-templates --tools read,grep,find,ls,bash --append-system-prompt <prompt> <task>` in `ctx.cwd`, all in parallel. The command is the running runtime plus pi's CLI script (`process.execPath` + `process.argv[1]`), because the Windows launcher `pi.cmd` can't be spawned without a shell. The prompt is the template body (frontmatter dropped) plus `PI_OUTPUT` (no `yield` tool: write the report as the final answer; bash for read-only commands only). The task is the scope with the diff command of the Review Mode entry, or `scopeTarget(scope)` for a typed scope (each reviewer then determines the diff). `bash` is there for git; on Windows pi's bash tool needs Git Bash. The child loads none of the user's extensions (built-in MCP included, and creview itself once installed), skills or prompt templates, because they could override the reviewer prompt and its output format; the built-in tools don't depend on them. Context files (`AGENTS.md`, `CLAUDE.md`) stay on, so the repository's own rules still inform the review. Trade-off: a provider that only a pi extension registers passes the pre-flight (the parent has it) but is unknown in the child, so that reviewer fails; providers from `models.json` and built-in ones work.
- **Result:** the text of the last assistant `message_end`; `stopReason` `error`/`aborted`, a non-zero exit, an empty answer or the 20-minute timeout (`TIMEOUT_MINUTES`) is a failure. The status line shows `creview: <n>/<total> reviewers done · Esc cancels`; in the TUI Esc (`isKey(data, "\x1b")`, consumed by `onTerminalInput`) and `session_shutdown` abort every child and notify `Cancelled; nothing changed.`.
- **Synthesis:** the reports go to the main session (`pi.sendUserMessage`, as a follow-up when not idle) with the scope, a coverage list (`Reported`, `Failed (no report): reviewer-x (<error>)`, `Skipped (pi can't run their model): …`, and a request to say which reviewers failed or were skipped), each report in `<report reviewer=… model=…>`, and `**Synthesize & Cross-Validate**:` followed by the same `synthesis` bullets as omp, naming the reviewers that reported. If every spawned reviewer failed, nothing is sent: error `Every reviewer failed: reviewer-a (<error>), …`.

## Data model

- **Single source of truth:** one `creview.json` holds shared reviewer models and host-local preset members: `{ "reviewers": { "<name>": "<provider/id[:level]>", ... }, "presets": { "omp": { "<preset>": ["<name>", ...] }, "pi": { "<preset>": ["<name>", ...] } } }`, 2-space indent, trailing newline, `reviewers` sorted by name on every write. Nothing reads models out of markdown.
- **Host-local operations:** preset types distinguish the host maps from an individual preset map; shared helpers select the current host's map. Every preset menu, List (including no UI), typed `/creview <preset>`, name collision check, create, remove, add and rm uses only that map. Equal preset names across hosts are independent. Writes preserve the other host's map and all shared reviewers; omp agent generation still covers every shared reviewer, regardless of preset membership or host.
- **Legacy migration:** read a flat `presets: { "<preset>": ["<name>", ...] }` entirely as omp presets, with pi empty. Arrays under names `omp` or `pi` are legacy presets too, not host sections. Reading does not rewrite the file; every successful write uses the new nested format, retaining both hosts' data.
- **`agents/` is generated output:** `agents/reviewer-<name>.md` is rendered from `templates/reviewer.md` for every entry of `reviewers`: the `name:` line becomes `name: reviewer-<name>` and the whole `model:` list becomes the reviewer's model; the rest of the template is kept as is. Never edit these files by hand: edit the template or use the commands.
- **Sync (`renderAgents` + `syncAgents`):** runs at every `session_start` and after every successful add. It writes a file only when its content differs (unchanged files keep their mtime) and deletes every `agents/reviewer-*.md` whose name is not in `reviewers`. Everything is rendered and validated first (template present with a `name:` line and a `model:` list; every reviewer name `[a-z0-9-]+` and model `provider/id[:level]`), so a failure writes nothing. At `session_start` a failure is an error notification, never a throw.
- **Template:** `templates/reviewer.md` is the base reviewer prompt (`name: reviewer`, model `@slow`). Its `model:` list items must start with two spaces and a hyphen (`  - "..."`); the `MODEL_BLOCK` regex only matches that format. A template edit reaches every reviewer at the next session start.

## Code rules

- **Valid names:** preset and reviewer names match `[a-z0-9-]+`.
- **Validate before writing:** every check (names, collision, model shape, valid template and data) runs before the first disk write. Errors are reported with `ctx.ui.notify(..., "error")`.
- **Reading `creview.json` (`readData`):** only a missing file means "no presets". A file that can't be read or parsed, or has the wrong shape (top level not an object; `reviewers` not an object of strings; `presets` neither a legacy object of string arrays nor host sections containing objects of string arrays; a missing key is empty), throws `creview.json: <problem>`. Validate both host sections before any write or sync, including the inactive host, so malformed data is never silently discarded. Every write path and the `session_start` sync call `readData` first; an error syncs or writes nothing. The user fixes the file by hand.
- **No completions:** neither command has `getArgumentCompletions`. On `/creview` a preselected completion item would take Enter from the bare command, which opens the picker; `/creview-config` takes no arguments.
- **Keep it small:** one file, no classes, no extra options, no runtime imports from either host. Both commands share `run` (argument trim, error notification).

## Reloading and verifying

- **Code:** a change to `extensions/creview.ts` only takes effect after restarting the host (omp: `/exit`, then `omp -c`); a loaded module is never re-evaluated. In omp `/reload-plugins` neither loads new extensions nor reloads loaded ones. Restart both omp and pi after the host-separated preset update before either writes the shared file.
- **Config:** adding or removing the `extensions:` entry in `config.yml` is picked up by a running session (the package is imported or suspended live).
- **Data:** changes made by `/creview-config` apply on the next command run or `task` spawn, no restart needed. Hand edits of `creview.json` (for example a reviewer's model) or the template reach `agents/` at the next session start (or the next add).
- **Test omp without an LLM or the TUI:** copy this folder to a temporary directory and run `omp --mode rpc --no-session --no-title --no-extensions -e <tempdir>` from any directory. `--no-extensions` keeps the configured copy (this folder) from also registering the `/creview` commands; the `-e` package still loads, with its `agents/`. Send `{"type":"get_available_commands"}` (`creview` and `creview-config` once each) and prompts such as `/creview-config`, answering its `extension_ui_request` dialogs. Writes then land in the temporary copy only, so the real data stays untouched.
- **Test pi the same way:** with an empty temporary agent directory, `PI_CODING_AGENT_DIR=<tempagent> pi --mode rpc --no-session -e <tempdir>` (the temporary agent directory keeps the installed copy and the user's settings out). Send `{"type":"get_commands"}` and prompts such as `/creview-config`. Without credentials List marks every reviewer and `/creview` stops at the pre-flight error; a review needs a provider key in that environment (or a local OpenAI-compatible stub declared in `<tempagent>/models.json`).
- **Template regression (omp):** a sync of the temporary copy must leave every `agents/reviewer-*.md` byte-identical with an unchanged mtime.
